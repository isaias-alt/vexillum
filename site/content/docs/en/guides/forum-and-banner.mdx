Two commands let agents show you something richer than terminal text.

## forum: review in your browser

```bash
vx forum .vexillum/forum/plan.html
```

Agents write their artifacts to `.vexillum/forum/` in the project. `vx init` adds a `.vexillum/.gitignore` that keeps that folder out of git; any path you pass on the command line still works, including an old `.forum/` folder.

Serves an HTML file the agent wrote to your browser and carries your feedback back to it. One local server per user runs on `127.0.0.1` and stops itself when nothing is connected. You can chat, queue messages, fill in decision forms and annotate elements, then send it all to the agent. A Mermaid diagram becomes an editable whiteboard.

On the agent's side:

| Command | Does |
| --- | --- |
| `vx forum <file>` | opens or resumes the session, makes sure the listener runs, and returns right away |
| `vx forum inbox` | prints the feedback waiting for the commander; `--ack <uid>...` confirms what it handled |
| `vx forum reply <file>` | shows an answer in the panel and answers the round, without blocking |
| `vx forum poll <file>` | blocks until you send feedback; `--reply` shows an answer in the panel (manual fallback) |
| `vx forum poll --all` | one poll for every open session at once; `--reply-to <file>` says which session a reply answers |
| `vx forum end <file>` | ends the session |
| `vx forum stop` | shuts the background listener and server down |

Sessions are identified by the file's absolute path. forum is built into the binary: no Node, no `npx`, no network.

### The server stays put

The server tries hard not to move or disappear under an open tab:

- **Same port.** It records the port it bound in `~/.vexillum/forum/last-port` and prefers it on the next start (waiting a few seconds for the previous server to release it), so an open tab keeps working. Only if that port stays taken by something else does it fall back to a free one and record that.
- **No replacing a server in use.** After you upgrade vexillum, a running server may come from an older build. It is replaced by the new build only when it has no open session, no connected tab and no waiting poll. Otherwise the new `vx` reuses it when its protocol is compatible, and stops with an error telling you what to do when it is not (finish or end the sessions and close the tabs, or run `vx forum stop`). A server too old to report its activity is reused, never stopped.
- **Tabs recover on their own.** When the server does restart, an open tab shows a reconnecting banner and retries on its own against the same address. Sessions, queued messages and the transcript are restored from disk, and the session link keeps working.

### The listener and the inbox

An agent used to hold a blocking poll for every session, and the poll died when the agent got busy. A small background process now holds it instead: `vx forum listen` (hidden; `vx forum <file>` starts it when it is not running, one per user, guarded by a pid lock). It is plain code with no model behind it, so it can only forward. For every prompt you send from a session that was opened inside a vexillum project it:

1. writes the prompt, with every field and the paths of any attached images, to the project's durable inbox (`forum-inbox/<session>/<uid>.json`, one atomic file per prompt, so a crash or a redelivery never loses or duplicates one),
2. records a **forum wake**, one per session however many messages arrived,
3. posts one fixed line in the panel ("Received. Forwarded to the commander, who will answer here.") that does not count as an answer,
4. and only then acknowledges the server.

The commander is woken by the same Stop hook as for soldiers, with a line like `forum session <file>: 2 new messages (ended: false). Run vx forum inbox.` It runs `vx forum inbox`, which prints the unread prompts in the poll's output format (bounded in size, attachments by path only, as data), acts, answers with `vx forum reply <file> --reply "..."` and confirms with `vx forum inbox --ack <uid>...`. A prompt is shown again until it is confirmed, so a restarted commander loses nothing. **Send & End** forwards the final prompts with `ended: true`; only that authorizes the commander to implement.

A session opened outside any project has no commander to wake: the listener leaves it undelivered and `vx forum poll` works for it as before. The listener exits by itself when no session is open or every review window is gone, and `vx forum stop` stops it first.

### Several sessions at once

Every polled session needs a listener, and a poll dies when it delivers feedback, when its background task times out, or when the agent is busy. With several sessions open that used to leave some of them with nobody listening. `vx forum poll --all` fixes it with one listener for all of them:

- It covers every open session (sessions opened while it waits join it), so every panel shows the agent as listening.
- Each call delivers the feedback of one session, the one waiting longest, and prints its `session` and `file` so the agent knows which artifact to edit. `other_sessions_pending` says how many more are waiting; the next call delivers them.
- `--reply-to <file>` names the session a `--reply` answers.
- A session that ends while it waits is reported once as `ended`. `no_sessions` means none is open. `browser_disconnected` means every review window is gone.

`vx forum poll <file>` keeps working for a single session.

### A dying poll never loses feedback

A poll does not consume feedback by returning it. The prompts stay on the server until the command confirms it printed them. If the poll was killed, timed out or lost its output in between, running `poll` again delivers the same prompts again, marked `redelivered: true` with the same `uid`s and ahead of anything newer, so the agent can skip what it already applied. This survives a server restart.

### What the panel says about your agent

| State | Meaning |
| --- | --- |
| Relayed, waiting for the commander | the listener forwarded your latest round and nobody has answered it; shows the time since forwarding, and says so when no commander session is known for the project |
| Forwarding to the commander | only the listener is waiting; nothing is outstanding |
| Agent listening | a poll is open (a `poll --all` counts for every session it covers) |
| Agent working | the agent took your messages and has not polled or replied since; holds up to 15 minutes |
| Waiting for your agent to listen | no poll right now, but the agent was there in the last 30 seconds (a poll just ended, it just replied or opened the session); no warning yet, so it does not flicker between a reply and the next poll |
| Agent not listening | none of the above: ask your agent to poll |

After you press Send to Agent the **Agent is working on your feedback** overlay stays up until the commander really answers (a `vx forum reply`), the artifact changes, or you press **Stop waiting**. The listener's "Received" line and its polling again do not clear it.

The agent's playbook is the `forum` [skill](/docs/concepts/skills), installed by `vx init` (full text on [Skill: forum](/docs/reference/skills/forum)).

## banner: publish publicly

```bash
vx banner report.html
```

<Callout type="warn" title="This publishes to a third party">
  `banner` inlines local assets into the HTML and POSTs it to a third-party hosting service (ht-ml.app by default). The page is public unless you pass `--private` or `--password`. It is your decision, per page, to publish.
</Callout>

It prints the page URL and an `update_key`, shown **once** and never stored by vexillum. It is the only credential that can update or unpublish the page; lose it and the page can never be changed. `--unpublish` replaces the page with a placeholder behind a discarded password, since there is no real delete. See the [`banner` reference](/docs/reference/cli/banner) for every flag and size cap.
