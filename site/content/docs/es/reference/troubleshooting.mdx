description: Los errores que más probablemente encuentres, y qué significan.
---

Empezá con `vx doctor`: te dice qué falta. Los mensajes de error de vexillum están en inglés y se citan tal cual.

| Mensaje | Causa y solución |
| --- | --- |
| `project not initialized, run 'vx init' first` | `dispatch` no encontró `.vexillum/config.json`. Corré `vx init` en la raíz del proyecto. |
| `current directory is not a git repository` | `init` necesita un repositorio git. |
| `git is not installed or not on PATH (install it from https://git-scm.com)` | `init` y `doctor` no pudieron ejecutar `git`. Instalá git, o arreglá el `PATH` de esta shell. |
| `cannot dispatch from here, nothing was started:` seguido de `HERDR_WORKSPACE_ID is not set - dispatch must run from inside a herdr-managed pane`, `herdr is not on PATH` o `claude is not on PATH` | `dispatch` y `redispatch` lo revisan antes de crear una tarea, un camp o el sentinel, y listan todo lo que falta de una vez. Iniciá Claude Code en un pane que herdr administre e instalá lo que figure (`vx doctor` muestra las mismas indicaciones). Una tarea cuyo perfil usa el harness `pi` necesita `pi` en el `PATH` en lugar de `claude`, y una que usa `opencode` necesita `opencode` (1.x desde 1.18.29, o 2.x). |
| `this terminal belongs to the Herdr app (HC_TERMINAL_ID is set) but VX_BACKEND=herdr selects the herdr TUI - run <command> from a herdr TUI pane, or use the experimental app backend: set VX_BACKEND=hc (or unset VX_BACKEND and HERDR_PANE_ID so vx detects the app terminal)` (la causa puede decir en cambio `HERDR_PANE_ID is set too, so the herdr TUI stays selected`) | Corriste un comando desde una terminal de la app de Herdr, pero está seleccionado el backend de la TUI de herdr: o `VX_BACKEND=herdr` está definido, o hay una variable de pane de herdr junto a las propias de la app. Quitá `VX_BACKEND` (y `HERDR_PANE_ID`) para que vexillum detecte la terminal de la app, o hacé `export VX_BACKEND=hc` antes de iniciar el commander. Mirá [Cómo se elige el backend](/es/docs/guides/herdr-app-backend#cómo-se-elige-el-backend). |
| `VX_BACKEND=hc is set but HC_TERMINAL_ID is not - <command> must run from inside a Herdr app terminal` | El backend experimental de la app está seleccionado, pero este shell no es una terminal de la app de Herdr. Iniciá el commander desde una terminal de la app, o quitá `VX_BACKEND`. |
| `herdr-core is not on PATH (looked for herdr-core and hc)` o `no usable herdr-core binary: ...` | `VX_BACKEND=hc` necesita el CLI `hc` de herdr-core, y solo cuenta un binario cuyo `--version` imprime `hc x.y.z`. Instalalo con el comando que imprime `vx doctor`, o quitá `VX_BACKEND`. |
| `unknown VX_BACKEND "..." (want "herdr" or "hc")` | La variable tiene un valor que vexillum no conoce. Ponela en `hc`, o quitala para usar la TUI de herdr. |
| `task <id> was dispatched on the hc backend, but this command runs on the herdr one - set VX_BACKEND=hc and try again` (o `... dispatched on the herdr backend, but this command runs on the hc one - unset VX_BACKEND and try again`) | Un soldier pertenece al backend en el que se despachó. Corré el comando donde corrió el dispatch: una terminal de la app de Herdr (o `VX_BACKEND=hc`) para `hc`, un pane de herdr para la TUI de herdr. |
| `the sentinel already running (pid N, ...) watches soldiers on the herdr backend and cannot supervise this one on hc - stop it (kill N) so the next vx command starts one that can; a sentinel serves one backend at a time` (o al revés) | Una advertencia al despachar. Detené con `kill` el pid que nombra; el próximo comando `vx` inicia un sentinel para el backend en el que estás. Nunca uses `pkill`. |
| Los wakes nunca llegan con el backend hc | El hook Stop commiteado corre el primer `vx` que encuentra en el `PATH`. Un `vx` distinto primero en el `PATH`, como uno viejo de Homebrew, corre `sentinel await` sin conocer el backend hc ni la detección de la terminal de la app. Poné primero en el `PATH` el build que corrés (`command -v vx` muestra cuál encuentra el hook) y reiniciá el commander. |
| `model "sonnet" for harness pi must be provider/id` (de `models.json` o de `vx dispatch`) | Un perfil en el harness `pi` necesita un modelo `provider/id` como `anthropic/claude-sonnet-5`, y un nivel de thinking (`off` a `max`) como effort. Ver [Usar Pi](/es/docs/guides/using-pi). |
| `[warn] herdr integration for pi` en `vx doctor` | Falta la integración de Pi de herdr o está desactualizada, así que herdr lee el estado de un soldier de Pi de la pantalla. Corré `herdr integration install pi`. |
| `[warn] herdr integration for opencode` en `vx doctor` | Lo mismo para OpenCode, solo en el backend de la TUI de herdr. Corré `herdr integration install opencode`. Con el backend hc doctor no muestra esta línea: muestra `opencode status plugin`. |
| `opencode reported no status within 4s (agent_not_ready)` de `vx dispatch` con el backend hc | El plugin de estado que vexillum carga en un soldier de OpenCode no se cargó, así que herdr-core nunca vio un estado. Revisá que `opencode --version` sea 2.x (OpenCode 1.x se rechaza al despachar), corré `vx doctor` y leé la línea `opencode status plugin`. El archivo del plugin se reescribe en cada dispatch. |
| `terminal ... has never reported a status ... (agent_not_reporting)` de `vx dispatch`, `vx prompt` o `vx decide` con el backend hc | El prompt se tipeó una vez en una terminal que nunca informó un estado, así que vexillum no puede ver si lo tomó y no lo tipea de nuevo (se encolaría dos veces). Mirá la terminal del soldier en la app de Herdr. Con OpenCode la causa suele ser la misma que `agent_not_ready` de arriba. |
| `[warn] OpenCode V1 shadowing V2 in PATH` en `vx doctor` | Un `opencode` 1.x más viejo va primero en el `PATH` y tapa a uno 2.x. Un soldier se despacha con el primero que se encuentra, así que poné primero la serie que querés. |
| `cannot start this soldier on <model>: OpenCode has no provider ...` (o `... has no model ...`, o `... has no variant ...`) | En OpenCode 2.x, dispatch comprueba el provider, el modelo y el variant del perfil contra lo que OpenCode lista para el camp y nombra lo que sí existe. Corregí el perfil (`opencode models` lista los modelos) y después hacé `vx strike` de la tarea fallida. Ver [Usar OpenCode](/es/docs/guides/using-opencode#qué-modelo-recibe-un-soldier). |
| `the OpenCode background service is not available: ...` desde `vx dispatch` | En 2.x vexillum levanta él mismo el servicio en segundo plano de OpenCode cuando no está corriendo, y no pudo. El error trae el mensaje del propio OpenCode. Corré `opencode service status`, después `opencode service start`, y despachá de nuevo. |
| `task <id> was dispatched on opencode 2.x but opencode 1.x ... is installed now` (o al revés) en `vx redispatch` | Una tarea se relanza en la serie de OpenCode con la que se despachó. Instalá esa serie, o hacé strike de la tarea y despachá una nueva. |
| `running from inside ... which looks like a vexillum-managed camp` | Estás en una ruta bajo `~/.vexillum`. Volvé con `cd` a la raíz real del proyecto. |
| `not running in a terminal, so nothing was changed.` | `init` o `upgrade` no encontró una terminal donde preguntar. Volvé a correr con `--yes` (sumá `--skills` o `--no-skills` para decidir sobre las skills). |
| `no answer (input closed or not understood) - nothing further was changed; re-run with --yes to accept without questions` | Una pregunta no tuvo una respuesta utilizable, así que la corrida se detuvo. Volvé a correr, o pasá `--yes`. |
| `AGENTS.md: the vexillum block was edited by hand, so it is left as it is` | Editaste dentro del bloque. `vx upgrade --force` lo reemplaza después de guardar el tuyo en `.vexillum/agents-md-slot.backup.md`. Ver [El slot de AGENTS.md](/es/docs/concepts/agents-md-slot). |
| `AGENTS.md: the vexillum block is malformed` | Marcadores rotos. `vx upgrade` lista las reparaciones y pregunta antes. |
| `a sentinel is already running (pid N)` | Está bien: hay uno por máquina. No inicies otro. |
| `[warn] sentinel` en `vx doctor`: más de un sentinel vivo, otra versión que el binario, o un binario que cambió desde que arrancó | Un sentinel desactualizado sigue corriendo después de un upgrade o rebuild. Normalmente se retira solo en segundos; si no, detené el pid que nombra doctor con `kill <pid>`. El siguiente `vx dispatch`, `vx prompt` o `await` del sentinel arranca uno al día. Nunca uses `pkill`. Ver [Mantenerse al día](/es/docs/concepts/sentinel#mantenerse-al-día). |
| `vx: not found, so the sentinel Stop hook cannot wake the commander ...` (stderr del hook) o `[warn] sentinel Stop hook finds vx` en `vx doctor` | El shell del hook no tiene `vx` en su `PATH` ni hay uno en `~/.local/bin`, Homebrew o `/usr/local/bin`. Instalá `vx` en alguno de esos lugares, o poné su directorio en el `PATH`. Si el hook se escribió con un `vx sentinel await` pelado, corré `vx upgrade` para reescribirlo. Ver [Sentinel](/es/docs/concepts/sentinel#el-hook-no-depende-de-tu-path). |
| `[warn] commanders share one wake queue` en `vx doctor`, o uno de dos commanders nunca se entera de que un soldier terminó | Dos commanders (por ejemplo Claude Code y Pi) están vivos en un mismo proyecto y un wake se entrega una sola vez, al primero que lo pide. Mantené un commander por proyecto; el otro puede ponerse al día con `vx status` y `vx forum inbox`. Ver [Dos commanders en un proyecto](/es/docs/concepts/sentinel#dos-commanders-en-un-proyecto). |
| `[warn] pending wakes in <project>` en `vx doctor`, o un commander que nunca oye a los soldiers que despachó en otro repositorio | Hay wakes esperando en un proyecto donde no corre ningún `vx sentinel await` ni hay un commander registrado. Los soldiers despachados por esta versión ponen sus wakes en el proyecto propio del commander, así que estos son más viejos, o el commander lleva más de los 55 minutos del await sin turno. Los entrega el próximo turno de un commander en ese proyecto, o `vx sentinel drain` corrido desde él. Un wake de más de 7 días está vencido: se borra y doctor no advierte por él. Mirá [Un commander en otro proyecto](/es/docs/concepts/sentinel#un-commander-en-otro-proyecto). |
| `.claude/settings.json has invalid JSON, leaving it untouched` | Arreglá el JSON y volvé a correr `vx init` para agregar el hook. |
| `no tasks yet in this project.` después de mover el proyecto | La clave de estado sigue a la ruta; ver [Estado](/es/docs/concepts/state). |

## Landing y strike

| Situación | Qué hacer |
| --- | --- |
| `land refused` | Tu checkout está sucio, o la branch divergió de la base. Commiteá o hacé stash, o pedile al soldier que haga rebase. Ver [Missions en paralelo](/es/docs/guides/parallel-missions). Un checkout sucio suele ser solo el scaffold de `init` sin commitear. |
| `landed, but automatic strike failed` | El merge no se deshace. Corré `vx strike <task-id>` a mano. |
| `strike refused` | El camp tiene cambios sin commitear o commits sin aterrizar. Aterrizá el trabajo primero. Para una mission enviada con ship, el rechazo dice que mergees el pull request y corras `git pull` en la branch base, y reintentes. Con `gh` con sesión iniciada, un PR mergeado cuyo commit de merge está en la base local cuenta como aterrizado. Ver [Cómo termina](/es/docs/guides/land-vs-ship#cómo-termina). |
| `strike refused: ... merge commit is not on <base> yet` | El PR mergeó en GitHub pero tu base local todavía no lo tiene. Corré `git pull` en la branch base y después `vx strike` de nuevo. |
| El general confirmó que el trabajo del camp ya está en la base o abandonado, y strike igual se niega | `vx strike <task-id> --discard` hace strike igual e imprime cada commit y cambio que descartó. Solo con la aprobación del general. |
| `strike refused: scout task ... has no report` | El reporte es el producto del scout. Hacé que lo escriba, o pasá `--force`. |
| `'gh' is not installed` | `ship`, y aterrizar un PR enviado, necesitan el GitHub CLI. |
| `vx: tribunal failed at <step>, refusing to push or open a pull request` | Falló un paso del tribunal; no se hizo push de nada. Arreglalo en el camp y volvé a hacer ship. |
| `review blocked: N blocking finding(s)` | La revisión adversarial encontró un error o warning (info nunca bloquea). Leé los hallazgos en la salida; arreglalos en el camp, o reintentá con `ship --fix` para los `auto-fix`. |
| `review blocked: incomplete coverage` | El revisor no reportó haber leído todos los archivos cambiados. Volvé a hacer ship. |
| `task ... is running, not interrupted` | Solo una tarea `interrupted` puede re-despacharse. |

## Un soldier parece atascado

Mirá `vx status`. `blocked` te está esperando: usá [`decide`](/es/docs/reference/cli/decide). `unconfirmed` o `interrupted` requieren mirar el camp; ver [Blocked e interrupted](/es/docs/guides/blocked-and-interrupted). Si el commander nunca reporta un soldier que terminó, confirmá que el sentinel corre (`~/.vexillum/sentinel.log`) y que `vx doctor` reporta el hook `Stop` como registrado y encontrando vx (`[ok] sentinel Stop hook finds vx`).
