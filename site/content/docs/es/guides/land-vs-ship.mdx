---
title: Land vs ship
description: Mergeá una mission localmente, o enviala por el pipeline tribunal a un pull request real.
---

Una mission terminada sale de su camp de dos maneras. Las dos son explícitas, y ninguna es silenciosa.

| | `vx land` | `vx ship` |
| --- | --- | --- |
| Resultado | fast-forward local de tu checkout | un pull request real de GitHub |
| Pipeline de revisión | ninguno; la revisaste vos | lint, tests, una revisión adversarial, un chequeo de docs |
| Necesita | un checkout limpio | `gh` instalado |
| Sale de la máquina | no | sí, hace push a `origin` |

Por defecto el commander pregunta antes de aterrizar. Una vez que le decís que aterrice sin preguntar, puede saltear ese paso en el proyecto.

## Land

```bash
vx land <task-id>
```

Hace fast-forward del checkout de tu proyecto hasta la branch de la mission, y después hace release del camp y cierra su pane. Se niega, dejando todo intacto, si tu checkout está sucio o la branch divergió de la base. Nunca fuerza ni hace rebase.

## Ship

```bash
vx ship <task-id>
```

Corre, en orden, dentro del camp de la mission, y se detiene en el primer fallo sin hacer push de nada:

1. **lint** - `go vet ./...` en un proyecto Go, `npm run lint --if-present` en uno Node;
2. **tests** - `go test ./...` o `npm run test --if-present`;
3. **review** - una revisión adversarial del diff hecha por una sesión nueva de Claude Code (ver abajo);
4. **docs** - en proyectos Go, las declaraciones exportadas nuevas deben llevar un comentario de documentación.

### La revisión adversarial

La revisión corre en una sesión nueva de Claude Code (nunca una reanudada) que no tiene nada del contexto del autor. Recibe la branch, los commits base y objetivo y la lista de archivos cambiados que calculó vexillum - no el diff. Lee el diff ella misma con `git`, asume que el cambio está mal e intenta romperlo: correctness, casos borde, manejo de errores, concurrencia, seguridad y autorización, regresiones y la calidad de los tests nuevos. Un hallazgo necesita un escenario de fallo concreto del uso previsto del cambio, y cada clase de defecto se reporta una sola vez con todos sus sitios hermanos. Corre con `sonnet` en esfuerzo `high` y no corre los tests (ya los corrió el paso anterior).

Cuando la mission tiene prompt, cada componente que el cambio introdujo también se juzga contra ese enunciado más las instrucciones que el general dio después, con `vx prompt` y `vx decide`. Esas quedan registradas en la tarea como amendments (con fecha y el comando de origen, en `vx status --json`) y se listan después del prompt, en orden, así que un componente que pediste más tarde no se reporta como no pedido. Solo esos dos comandos escriben amendments, en el archivo de estado de la tarea y nunca en un archivo del camp, así que un soldier no puede ampliar su propio mandato. Lo que no pidió ni el prompt ni un amendment se reporta como warning con remedio "quitarlo". Una mission sin prompt omite esta pasada, y `ship` lo dice.

El revisor devuelve JSON: hallazgos (`file`, `line`, `severity` error/warning/info, `action` ask-user/auto-fix/no-op, descripción, escenario de fallo, sitios hermanos), los `reviewed_paths` que realmente leyó y un nivel de riesgo. Si el JSON no valida, la revisión se reintenta (hasta dos veces más). Después:

- cualquier hallazgo de severidad **error o warning bloquea el ship**, incluidos los `ask-user`, que necesitan tu decisión; los **info** no bloquean;
- un archivo cambiado que falta en `reviewed_paths` cuenta como no revisado y hace fallar el paso;
- sin JSON válido tras los reintentos, o un timeout, el paso falla. Ninguno de los dos es jamás un pass.

Los hallazgos se imprimen en la salida de `vx ship`. Si el ship pasa, los hallazgos info se agregan al cuerpo del pull request bajo Tribunal notes.

### Revisar, arreglar, revisar (opt-in)

```bash
vx ship <task-id> --fix [--max-rounds 2] [--timeout 20m]
```

Sin `--fix`, una revisión que bloquea solo rechaza el ship e imprime los hallazgos. Con `--fix`, los hallazgos marcados `auto-fix` van a un fixer headless en el camp, que arregla la invariante en todos los sitios hermanos (y prefiere quitar un componente no requerido a endurecerlo). vexillum commitea su trabajo, corre lint y tests de nuevo, y un revisor nuevo vuelve a revisar, sabiendo que los commits del fixer son código sin revisar y deben cumplir el mismo estándar. Quien prescribió una corrección jamás la certifica.

Los hallazgos `ask-user` nunca se auto-corrigen: si algún hallazgo bloqueante necesita a un humano, `ship` rechaza sin ronda de arreglo. `--max-rounds` limita las rondas de arreglo (por defecto 2); agotarlas sin una revisión que pase rechaza el ship. `--timeout` limita cada corrida de revisor o fixer (por defecto 20 minutos).

Sin `go.mod` ni `package.json`, lint y tests pasan con una nota de que no se detectó nada. Es sincrónico: cuando `ship` vuelve, todo el pipeline terminó. Solo después de que pasan todos los pasos hace push de la branch del camp a `origin` y corre `gh pr create`. Ningún agente decide si eso ocurre ni cuándo: es la única acción con un efecto irreversible fuera de la máquina.

Una mission en `done` o `shipped` puede enviarse de nuevo para empujar seguimientos al mismo PR; vuelve a correr el pipeline completo primero.

### El texto del pull request

El pull request es público, así que `vx ship` nunca copia en él el prompt del despacho ni sus enmiendas. El título es el subject del único commit de la branch, o de su commit `feat`, `fix` o `docs` más reciente, o de su primer commit, cortado a unos 72 caracteres. El cuerpo se arma con hechos: una sección **What** (los subjects de los commits como lista), una línea **Changes** (archivos cambiados, inserciones, borrados y las áreas de primer nivel tocadas), una línea **Verification** (los pasos del tribunal que pasaron, las rondas de revisión y las de arreglo), los hallazgos info de la revisión bajo **Tribunal notes**, y un pie de una línea que nombra la mission.

```bash
vx ship <task-id> --title "feat: titulo conciso" --body-file description.md
```

`--title` reemplaza el título derivado. `--body "<texto>"` o `--body-file <ruta>` (`-` lee la entrada estándar; no se pueden combinar) reemplaza la sección What; Changes, Verification, Tribunal notes y el pie se mantienen. Todo lo que viene del camp, del revisor o de un cuerpo provisto se sanea antes de publicar: se descartan las líneas con una ruta absoluta de home (`/Users/...`, `/home/...`), un puerto de localhost o algo que parezca un secreto, y también cualquier línea que cite el prompt de la mission; `vx ship` informa cuántas descartó. Un `--title` que no pasa la misma comprobación se rechaza antes de que corra el tribunal. Volver a enviar una mission cuyo pull request ya está abierto no toca el texto del pull request.

## Aterrizar una mission enviada

```bash
vx land <task-id>
```

Para una tarea enviada, `land` mergea el **pull request real**. Requiere `gh` y se niega salvo que el PR esté abierto, no sea draft, sea mergeable y todos los checks estén en verde; el merge queda atado al head exacto que acaba de verificar. No hace release del camp: la branch sigue en vuelo hasta que el PR realmente se mergee.
