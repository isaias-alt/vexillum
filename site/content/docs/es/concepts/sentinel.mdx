El sentinel es lo que te deja alejarte. Vigila a cada soldier despachado e interrumpe al commander - y por lo tanto a vos - solo cuando uno termina.

## Qué hace

Corre un sentinel por máquina. Cada 5 segundos consulta el estado en vivo de herdr de cada tarea en `running`, en todos los proyectos que vexillum haya visto. Cuando una tarea termina (done o blocked) persiste el nuevo status y escribe un **wake** durable bajo el proyecto de esa tarea (`wakes/<task-id>.json`). También detecta tareas que pasaron a `interrupted` o `unconfirmed`, y solo después de confirmarlo durante una ventana, no por una sola observación.

También vigila a los soldiers ya terminados cuyo camp sigue en su lugar: si uno vuelve a trabajar (le mandaron un prompt después de terminar), el sentinel devuelve su tarea a `running` sin un wake, así que su próximo fin es una transición como cualquier otra. Ver [Dar seguimiento a un soldier terminado](#dar-seguimiento-a-un-soldier-terminado).

`vx dispatch` inicia un sentinel automáticamente si no hay uno corriendo. Si eso falla avisa por stderr, y podés correr `vx sentinel` vos mismo en segundo plano. Un segundo sentinel se niega a arrancar y nombra el pid del primero: el reclamo es un lock que el kernel suelta cuando el proceso muere, así que un crash nunca deja uno viejo colgado y dos sentinels no pueden correr a la vez. Su pid, el build desde el que corre y su log están en `~/.vexillum/sentinel.pid`, `~/.vexillum/sentinel.json` y `~/.vexillum/sentinel.log`.

Un wake se entrega como mucho una vez y solo mientras siga siendo noticia. Al leerlo, el sentinel lo descarta si el status de la tarea cambió desde entonces (la respondiste, le mandaste otro prompt o la hiciste ship), si su camp fue liberado o si su mission ya aterrizó, así que una acumulación de wakes mientras nadie escuchaba nunca se reproduce como una ráfaga de avisos viejos. Corré `vx status` para ver el panorama completo después de una ausencia larga.

El mismo hook también lleva **forum wakes**: cuando un usuario manda feedback desde un panel de revisión de [forum](/es/docs/guides/forum-and-banner), el listener de forum (no un soldier) lo guarda en el inbox del proyecto y registra un wake bajo `wakes/forum/`, uno por sesión. `vx sentinel await` y `drain` lo informan como `forum session <file>: 2 new messages (ended: false). Run vx forum inbox.` Se entrega una vez y se descarta si sus mensajes ya fueron confirmados; la fuente de verdad es el inbox, no el wake.

Un soldier solo queda registrado como `blocked` por una línea `needs-decision:` que escribió en su último turno, después del final del prompt despachado, con texto real. La línea de plantilla del prompt, o cualquier placeholder entre ángulos, nunca cuenta, ni tampoco una pregunta que ya respondiste o descartaste.

## Mantenerse al día

Un sentinel es un proceso de larga vida, así que puede sobrevivir al binario con el que arrancó. Uno viejo seguiría reescribiendo el estado de las tareas con lógica vieja, que es como antes se borraban campos escritos por un build más nuevo. Dos cosas lo evitan:

- **Las tareas conservan lo que no entienden.** Guardar una tarea cambia solo los campos que el build en ejecución conoce y vuelve a escribir tal cual cualquier otro campo de primer nivel, así que un proceso viejo no puede borrar lo que registró uno más nuevo.
- **El sentinel se retira cuando cambia su binario.** Registra el build desde el que arrancó (versión y archivo ejecutable) en `~/.vexillum/sentinel.json` y lo revisa después de cada pasada. Cuando ese archivo fue reemplazado en disco (un rebuild, `brew upgrade`) termina la pasada en curso, suelta su lock y sale. Compara el archivo y no solo la versión, porque todo `go build` común reporta `dev`.

El siguiente `vx dispatch`, `vx prompt` o `await` del hook Stop arranca entonces un sentinel nuevo desde el binario nuevo, y el reemplazo espera un momento a que el viejo suelte el lock en vez de rendirse. Un `await` lo verifica en cada consulta, así que una sesión de commander que solo está esperando recibe un sentinel nuevo en segundos.

`vx doctor` avisa cuando hay más de un proceso sentinel vivo, cuando el sentinel vivo es de otra versión que el binario que corre doctor, cuando su ejecutable cambió desde que arrancó, o cuando es anterior a este seguimiento. Cada aviso nombra el pid que hay que detener con `kill`, y el siguiente dispatch arranca uno al día. Doctor nunca detiene un proceso por su cuenta.

## Cómo se despierta al commander

`vx init` registra un hook `Stop` asíncrono en el `.claude/settings.json` del proyecto:

```json
{
  "type": "command",
  "command": "sh -c 'for v in \"$(command -v vx 2>/dev/null)\" \"$HOME/.local/bin/vx\" /opt/homebrew/bin/vx /usr/local/bin/vx /home/linuxbrew/.linuxbrew/bin/vx; do [ -f \"$v\" ] && [ -x \"$v\" ] && exec \"$v\" sentinel await; done; echo \"vx: not found, so the sentinel Stop hook cannot wake the commander. Install vx (brew or curl) or put its directory on PATH, then run: vx doctor\" >&2; exit 0'"
}
```

registrado con `asyncRewake` y un timeout de una hora. El comando es un wrapper POSIX `sh -c` de una línea que termina corriendo `vx sentinel await`; ver [El hook no depende de tu PATH](#el-hook-no-depende-de-tu-path). `await` se bloquea, revisando cada 5 segundos, hasta que llega un wake para *este proyecto*, y entonces responde `{"decision":"block","reason":...}` para que Claude Code reporte el cambio en lugar de terminar su turno en silencio - incluso si el turno terminó antes de que el soldier acabara. El reason lista cada cambio, por ejemplo `- mission <task-id>: running -> done`.

| Subcomando | Comportamiento |
| --- | --- |
| `vx sentinel` | consulta para siempre (corrélo en segundo plano) |
| `vx sentinel await` | se bloquea hasta que llega un wake o se agota el tiempo; lo que llama el hook |
| `vx sentinel drain` | revisa una vez, al instante: una decisión `block` si hay algo pendiente, `{}` si no |

Fuera de un pane administrado por herdr (sin `HERDR_WORKSPACE_ID`), `await` y `drain` salen en silencio: el hook se commitea con el proyecto, así que también se dispara en turnos de Claude Code ajenos, como la revisión headless de un camp, que no tienen ningún soldier que esperar.

Cada `await` se registra en `~/.vexillum/sentinel-awaiters/` y nunca sobrevive al hook que lo lanzó. Sale solo cuando su proceso padre desaparece, y un `await` más nuevo de la misma sesión y proyecto reemplaza al del turno anterior, así que una sesión deja un proceso esperando, no uno por turno. Arrancar `vx sentinel` o cualquier `await` también detiene a los huérfanos que dejó una sesión muerta. A un proceso solo se le manda una señal después de verificar, por su archivo de pid y su línea de comando, que es un `vx sentinel await`, nunca por nombre.

## El hook no depende de tu PATH

Claude Code corre el hook en un shell que puede no haber leído nunca tu perfil, así que un `vx sentinel await` pelado puede fallar con `command not found` cuando vx vive en `~/.local/bin`. Entonces el commander nunca se despertaría, sin que nada lo avise. Por eso el comando registrado busca vx por su cuenta, en este orden:

1. `command -v vx`, el primer `vx` en el `PATH` del shell del hook;
2. `$HOME/.local/bin/vx` (el instalador con curl);
3. `/opt/homebrew/bin/vx` (Homebrew en Apple silicon);
4. `/usr/local/bin/vx` (Homebrew en macOS Intel, o una instalación manual);
5. `/home/linuxbrew/.linuxbrew/bin/vx` (Homebrew en Linux).

El primero que existe y es ejecutable se corre con `exec`, así que el proceso `await` sigue siendo hijo directo de quien lanza el hook. No se escribe ninguna ruta absoluta en `settings.json`, que se commitea y se comparte entre máquinas, ni se agrega ningún archivo extra a tu proyecto.

Si no encuentra ninguno, el hook no se queda callado: imprime una línea por stderr, `vx: not found, so the sentinel Stop hook cannot wake the commander. Install vx (brew or curl) or put its directory on PATH, then run: vx doctor`, y sale con 0 para no bloquear a Claude Code.

`vx doctor` lo verifica de verdad. Corre el comando registrado desde un entorno mínimo (`env -i` con solo `HOME` y `PATH=/usr/bin:/bin`) y reporta si encontró un vx, si el hook está registrado y si hay un sentinel corriendo:

```text
[ok] sentinel Stop hook - registered in .claude/settings.json
[ok] sentinel Stop hook finds vx - found with a minimal environment
[ok] sentinel - running, 1 Stop hook await(s) waiting
```

Un hook que no encuentra vx es un aviso (`warn`), no un fallo, y la línea nombra el arreglo: instalá vx donde el hook busca (`~/.local/bin` o Homebrew) y corré `vx upgrade` para reescribir un hook viejo.

`vx init` y `vx upgrade` migran las formas anteriores, un `vx sentinel await` pelado, el `vexillum sentinel await` previo al cambio de nombre y el `vexillum sentinel drain` sincrónico, al comando de arriba. Preguntan primero, como el resto de `upgrade`, y cualquier hook `Stop` tuyo que no sea de vexillum se conserva.

## Dar seguimiento a un soldier terminado

El sentinel reporta una tarea que *sale* de `running`, así que un soldier al que se le manda otro prompt después de terminar necesita que su tarea se reabra primero. Usá [`vx prompt`](/es/docs/reference/cli/prompt):

```bash
vx prompt <task-id> "agregá también una entrada al changelog"
```

Devuelve la tarea a `running`, entrega el texto y se asegura de que haya un sentinel vigilando, así que el próximo fin del soldier vuelve a despertar al commander. Solo se puede mandar un prompt a una tarea `done`, `shipped` o `unconfirmed` cuyo camp no fue liberado (una shipped pasa a `running` y se asienta como `done`, no `shipped`, porque los commits nuevos no están en su pull request hasta que `vx ship` corra de nuevo); una tarea `blocked` se responde con `vx decide` y una `interrupted` con `vx redispatch`.

Mandarle el prompt al pane a mano (`herdr agent prompt`) sigue funcionando como respaldo: el sentinel reabre una tarea terminada que ve trabajando otra vez. Esa detección es por polling, así que un seguimiento muy corto que termina entre dos polls puede escapársele, por eso `vx prompt` es el camino soportado.

Ver la [referencia de `sentinel`](/es/docs/reference/cli/sentinel) para el uso completo.
