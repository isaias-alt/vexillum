Empezá con `vx doctor`: te dice qué falta. Los mensajes de error de vexillum están en inglés y se citan tal cual.

| Mensaje | Causa y solución |
| --- | --- |
| `project not initialized, run 'vx init' first` | `dispatch` no encontró `.vexillum/config.json`. Corré `vx init` en la raíz del proyecto. |
| `current directory is not a git repository` | `init` necesita un repositorio git. |
| `HERDR_WORKSPACE_ID is not set - dispatch must run from inside a herdr-managed pane` | Iniciá Claude Code en un pane que herdr administre; `dispatch` y `redispatch` se niegan en otro lado. |
| `running from inside ... which looks like a vexillum-managed camp` | Estás en una ruta bajo `~/.vexillum`. Volvé con `cd` a la raíz real del proyecto. |
| `not running in a terminal, so nothing was changed.` | `init` o `upgrade` no encontró una terminal donde preguntar. Volvé a correr con `--yes` (sumá `--skills` o `--no-skills` para decidir sobre las skills). |
| `no answer (input closed or not understood) - nothing further was changed; re-run with --yes to accept without questions` | Una pregunta no tuvo una respuesta utilizable, así que la corrida se detuvo. Volvé a correr, o pasá `--yes`. |
| `AGENTS.md: the vexillum block was edited by hand, so it is left as it is` | Editaste dentro del bloque. `vx upgrade --force` lo reemplaza después de guardar el tuyo en `.vexillum/agents-md-slot.backup.md`. Ver [El slot de AGENTS.md](/es/docs/concepts/agents-md-slot). |
| `AGENTS.md: the vexillum block is malformed` | Marcadores rotos. `vx upgrade` lista las reparaciones y pregunta antes. |
| `a sentinel is already running (pid N)` | Está bien: hay uno por máquina. No inicies otro. |
| `[warn] sentinel` en `vx doctor`: más de un sentinel vivo, otra versión que el binario, o un binario que cambió desde que arrancó | Un sentinel desactualizado sigue corriendo después de un upgrade o rebuild. Normalmente se retira solo en segundos; si no, detené el pid que nombra doctor con `kill <pid>`. El siguiente `vx dispatch`, `vx prompt` o `await` del hook Stop arranca uno al día. Nunca uses `pkill`. Ver [Mantenerse al día](/es/docs/concepts/sentinel#mantenerse-al-día). |
| `vx: not found, so the sentinel Stop hook cannot wake the commander ...` (stderr del hook) o `[warn] sentinel Stop hook finds vx` en `vx doctor` | El shell del hook no tiene `vx` en su `PATH` ni hay uno en `~/.local/bin`, Homebrew o `/usr/local/bin`. Instalá `vx` en alguno de esos lugares, o poné su directorio en el `PATH`. Si el hook se escribió con un `vx sentinel await` pelado, corré `vx upgrade` para reescribirlo. Ver [Sentinel](/es/docs/concepts/sentinel#el-hook-no-depende-de-tu-path). |
| `.claude/settings.json has invalid JSON, leaving it untouched` | Arreglá el JSON y volvé a correr `vx init` para agregar el hook. |
| `no tasks yet in this project.` después de mover el proyecto | La clave de estado sigue a la ruta; ver [Estado](/es/docs/concepts/state). |

## Landing y release

| Situación | Qué hacer |
| --- | --- |
| `land refused` | Tu checkout está sucio, o la branch divergió de la base. Commiteá o hacé stash, o pedile al soldier que haga rebase. Ver [Missions en paralelo](/es/docs/guides/parallel-missions). Un checkout sucio suele ser solo el scaffold de `init` sin commitear. |
| `landed, but automatic release failed` | El merge no se deshace. Corré `vx release <task-id>` a mano. |
| `release refused` | El camp tiene cambios sin commitear o commits sin aterrizar. Aterrizá el trabajo primero. Para una mission enviada con ship, el rechazo dice que mergees el pull request y corras `git pull` en la branch base, y reintentes. Con `gh` con sesión iniciada, un PR mergeado cuyo commit de merge está en la base local cuenta como aterrizado. Ver [Cómo termina](/es/docs/guides/land-vs-ship#cómo-termina). |
| `release refused: ... merge commit is not on <base> yet` | El PR mergeó en GitHub pero tu base local todavía no lo tiene. Corré `git pull` en la branch base y después `vx release` de nuevo. |
| El general confirmó que el trabajo del camp ya está en la base o abandonado, y release igual se niega | `vx release <task-id> --discard` hace release igual e imprime cada commit y cambio que descartó. Solo con la aprobación del general. |
| `release refused: scout task ... has no report` | El reporte es el producto del scout. Hacé que lo escriba, o pasá `--force`. |
| `'gh' is not installed` | `ship`, y aterrizar un PR enviado, necesitan el GitHub CLI. |
| `vexillum failed at <step>, refusing to push` | Falló un paso del tribunal; no se hizo push de nada. Arreglalo en el camp y volvé a hacer ship. |
| `review blocked: N blocking finding(s)` | La revisión adversarial encontró un error o warning (info nunca bloquea). Leé los hallazgos en la salida; arreglalos en el camp, o reintentá con `ship --fix` para los `auto-fix`. |
| `review blocked: incomplete coverage` | El revisor no reportó haber leído todos los archivos cambiados. Volvé a hacer ship. |
| `task ... is running, not interrupted` | Solo una tarea `interrupted` puede re-despacharse. |

## Un soldier parece atascado

Mirá `vx status`. `blocked` te está esperando: usá [`decide`](/es/docs/reference/cli/decide). `unconfirmed` o `interrupted` requieren mirar el camp; ver [Blocked e interrupted](/es/docs/guides/blocked-and-interrupted). Si el commander nunca reporta un soldier que terminó, confirmá que el sentinel corre (`~/.vexillum/sentinel.log`) y que `vx doctor` reporta el hook `Stop` como registrado y encontrando vx (`[ok] sentinel Stop hook finds vx`).
