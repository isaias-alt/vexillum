# Referencias a los repositorios y/o proyectos

## Referencia directa:

__firstmate__: la base conceptual entera. Coordinador único que despacha subagentes en paralelo, worktrees aislados, dos task shapes, supervisión zero-token, restart-proof. Todo tu modelo mental sale de acá. Es LA referencia. [Repositorio](https://github.com/kunchenguid/firstmate)
__treehouse__: relevante desde la Capa 3. Es el manejo de worktrees reutilizables aislados, o sea tu concepto de camp. Además está en Go, así que te sirve doble: como referencia conceptual y como ejemplo de código Go real haciendo exactamente la plomería de worktrees que vas a escribir. [Repositorio](https://github.com/kunchenguid/treehouse)

## Referencia lateral, no ahora:

__herdr__: la socket API que el sentinel consulta en Capa 4. Cuando llegues a la supervisión, su doc es referencia obligada. [Docs de Herdr](https://herdr.dev/docs/)

## Estándar AXI (referencia conceptual, v2):

__axi.md__: el estándar Agent eXperience Interface. Diez principios de diseño de CLI agent-ergonomic: salida TOON token-efficient, schemas mínimos, operaciones combinadas, errores estructurados con exit codes, contenido antes que help. Todos los AXIs que consume Vexillum en v2 siguen este contrato. Es la referencia del formato, no una dependencia ejecutable. [Sitio](https://axi.md) · [Repositorio](https://github.com/kunchenguid/axi)

## Dependencias externas AXI (v2):

No son referencias conceptuales: son CLIs externos que Vexillum invoca. Se distribuyen como Agent Skills (`npx skills add <owner>/<repo> --skill <nombre> -g`, formato agentskills.io): el skill instalado es solo un stub de discovery, el agente aprende a usarlo usándolo, y el CLI real se baja on-demand con `npx -y <axi>` la primera vez. El binario Go no los instala ni los conoce más que para que `doctor` reporte si el skill está presente en disco. La columna "modo" indica quién los invoca una vez instalados: el commander por su cuenta, el soldier desde el prompt de su mission, o (a decidir) el binario como plomería.

__quota-axi__ (oficial, implementado en v2 - `doctor` reporta si está instalado): reporta ventanas de cuota/uso local de Claude, Codex, Cursor, Copilot, Grok y más, con señales derivadas (`runway`, `spendPriority`) pensadas para routing-aware agents - pero estrictamente data-only, el ruteo lo hace el consumidor. En v2 es consulta informativa: el general pregunta, el commander lo corre. No gatea despacho. Instalación real verificada: `npx skills add kunchenguid/quota-axi --skill quota-axi -g`. Modo: commander por prompt. [Repositorio](https://github.com/kunchenguid/quota-axi)
__lavish-axi__ (oficial, implementado en v2 - `doctor` reporta si está instalado): convierte artefactos HTML del agente en superficies de revisión colaborativa - fijar elementos/rangos de texto, editar diagramas Mermaid como whiteboards, feedback estructurado de vuelta al agente, con playbooks de fábrica para planes de producto/técnicos. En v2 se invoca bajo demanda para revisar planes; no reemplaza el loop de texto. Instalación real verificada: `npx skills add kunchenguid/lavish-axi --skill lavish` (sin `-g` - a diferencia de quota-axi, el nombre del skill es `lavish`, no `lavish-axi`). Modo: commander por prompt. [Repositorio](https://github.com/kunchenguid/lavish-axi)
__chrome-devtools-axi__ (oficial, implementado en v2 - `doctor` reporta si está instalado, y el core lo soporta): automatización de browser (navegar, clickear, llenar, extraer) con operaciones combinadas y filtrado por query sobre chrome-devtools-mcp. Su propio skill le dice al agente cuándo NO usarlo (web search o páginas estáticas: fetch/curl). Habilita soldiers cuya mission necesita navegador: probar frontend en vivo, investigar en la web, operar en plataformas. Único AXI que toca el core: un proceso "bridge" persistente por sesión (`CHROME_DEVTOOLS_AXI_SESSION=<nombre>`, estado en `~/.chrome-devtools-axi/sessions/<nombre>/bridge.pid`) no muere solo cuando el pane de herdr del soldier se cierra. `vexillum` namespacea cada soldier con `CHROME_DEVTOOLS_AXI_SESSION=vx-<task-id>` desde que arranca su pane (`herdr tab create --env`, verificado en vivo) y `vexillum redispatch` cierra ese bridge huérfano al descartar el camp muerto - extensión del criterio de terminado de A.2. Instalación real verificada: `npx skills add kunchenguid/chrome-devtools-axi --skill chrome-devtools-axi -g`. Modo: soldier por prompt de mission. [Repositorio](https://github.com/kunchenguid/chrome-devtools-axi)
__gh-axi__ (oficial, no usado por B.4): operaciones de GitHub (issues, PRs, workflow runs, releases) envolviendo el `gh` CLI oficial con salida agent-ergonomic. **Corrección**: se pensaba que era el mecanismo con el que no-mistakes abre PRs - investigado en v2 y no es así, no-mistakes tiene su propia integración de GitHub y no necesita gh-axi para nada (ver `docs/no-mistakes.md`). Queda fuera del catálogo activo de Vexillum hasta que una mission concreta necesite operar sobre issues/releases/workflow runs por su cuenta. [Repositorio](https://github.com/kunchenguid/gh-axi)

## Herramientas standalone (no AXI, v2):

No siguen el modelo "Agent Skill instalado con `npx skills add`" de la sección anterior - son binarios reales, instalados por su cuenta (típicamente `curl`, igual que Vexillum mismo).

__no-mistakes__ (oficial, implementado en v2 - `doctor` reporta si está instalado y si el proyecto está gateado; comando `vexillum ship`): pone un git remote local (`no-mistakes`) delante del remote real de un repo. `git push no-mistakes <branch>` corre un pipeline propio (review, test con evidencia, docs, lint) en un worktree aislado propio de la herramienta, y solo si todo pasa reenvía la rama al remote real y abre el PR - con su propia integración de GitHub, sin gh-axi. Instalación real (no es un Agent Skill): `curl -fsSL https://raw.githubusercontent.com/kunchenguid/no-mistakes/main/docs/install.sh | sh`, seguido de `no-mistakes init` una vez por repo (crea el remote `no-mistakes` y, de paso, instala su propio skill `/no-mistakes` a nivel usuario - eso lo maneja la herramienta, no Vexillum). `vexillum ship <task-id>` dispara el push de forma determinista para una mission `done`; el resto del pipeline (y la apertura del PR) es 100% de la herramienta. Diseño completo en `docs/no-mistakes.md`. [Repositorio](https://github.com/kunchenguid/no-mistakes)
